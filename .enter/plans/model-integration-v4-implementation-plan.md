# AIPictureBookStudio 大模型接入平台 V4 实施计划

## 目标

基于 `docs/superpowers/specs/2026-04-27-model-integration-v4-design.md`，将当前项目逐步迁移到 `Next.js` 技术栈，并落地一套支持文本模型与图像模型双域解耦的生产级模型接入平台。

实施计划目标：

- 控制迁移风险，避免一次性重构过大
- 优先建立稳定的工程骨架与核心抽象
- 保证每个阶段都可单独验证与回滚
- 先打通文本链路，再接入图像链路，再上线配置中心

---

## 实施原则

### 1. 先骨架，后接厂商

先完成 `Next.js` 工程迁移、workspace 拆分、共享内核、工厂与配置加载器，再接具体厂商 API，避免边开发边推翻底层结构。

### 2. 双域分阶段接入

- 文本模型域先落地
- 图像模型域后落地

这样可以先验证抽象、异常、日志、热更新链路是否成立，再扩展到出图能力。

### 3. 配置中心最后上线

在双域策略、工厂、健康检查都稳定前，不急于开放 `/settings/models`。先让底层跑通，再把复杂配置界面接上，降低联调难度。

### 4. 每阶段必须可验收

每个阶段都要有：

- 明确交付物
- 明确验证方式
- 明确回滚边界

## 阶段拆分

## Phase 0：准备阶段

### 目标

完成实施前准备，冻结当前前端原型状态，明确迁移边界和基线。

### 任务

1. 记录当前项目现状
   - 梳理现有页面、状态、模拟生成逻辑、导出能力
   - 标记必须迁移模块与可后迁移模块

2. 建立迁移基线
   - 确认现有前端可正常运行
   - 记录当前 lint、构建状态
   - 记录当前已有设计文档与需求约束

3. 输出迁移映射表
   - Vite 路由 -> Next.js App Router
   - 现有 context/state -> Next.js 下保留或重构方式
   - 现有页面组件 -> 新目录映射

### 交付物

- 当前项目模块迁移清单
- 路由迁移清单
- 状态迁移清单

### 验收

- 能清楚回答“哪些代码先迁、哪些后迁、哪些保留不动”

## Phase 1：工程骨架迁移

### 目标

建立 `Next.js monorepo` 基础结构，并让现有前端主流程在新骨架中可运行。

### 任务

1. 建立 workspace
   - 新增 `pnpm-workspace.yaml`
   - 拆分 `apps/web`
   - 预留 `packages/*`

2. 初始化 `Next.js` 应用
   - 启用 `App Router`
   - 启用 TypeScript
   - 接入 Tailwind
   - 引入必要 UI 基础设施

3. 迁移基础前端能力
   - 全局样式
   - 布局
   - 通用组件引用路径
   - toast、query client、provider 体系

4. 迁移主业务页面
   - Studio 主流程
   - Editor 页面
   - NotFound 页面

5. 兼容原状态管理
   - 先保留现有 context/reducer 思路
   - 暂不在本阶段重做业务状态架构

### 交付物

- `apps/web` 可启动
- 主业务页面在 `Next.js` 下可访问
- 原有主要交互不回退

### 验收

- `apps/web` 本地可运行
- Studio 主流程可进入各阶段
- Editor 页面可打开
- 现有导出相关页面不报阻断性错误

### 回滚边界

- 若迁移中断，保留原 Vite 项目作为对照基线

---

## Phase 2：共享内核与双域包骨架

### 目标

建立文本模型域、图像模型域、共享内核三大包的最小可运行结构。

### 任务

1. 建立 `shared-model-kernel`
   - 标准响应类型
   - 通用错误类型
   - traceId 工具
   - logger 接口
   - retry / timeout / rate limiter 抽象

2. 建立 `text-model-core`
   - `TextModelStrategy`
   - 文本注册表
   - `TextModelFactory`
   - 文本域依赖装配器

3. 建立 `image-model-core`
   - `ImageModelStrategy`
   - 图像注册表
   - `ImageModelFactory`
   - 图像域依赖装配器

4. 建立服务端装配入口
   - `apps/web/src/server/container`
   - `apps/web/src/server/loaders`
   - `apps/web/src/server/services`

### 交付物

- `packages/shared-model-kernel`
- `packages/text-model-core`
- `packages/image-model-core`
- 基础 factory / registry / strategy interface

### 验收

- 三个 package 能被 `apps/web` 正确引用
- 工厂可以基于 mock 配置返回 mock 策略实例
- 文本域和图像域依赖完全分离

---

## Phase 3：配置加载器与热更新基础设施

### 目标

建立 `config/models.yaml` 读取、环境变量解析、版本化配置缓存与热更新事件机制。

### 任务

1. 实现配置协议
   - 文本模型配置结构
   - 图像模型配置结构
   - 高级参数类型定义

2. 实现 `model-loader`
   - 读取 `config/models.yaml`
   - 解析 `${ENV_NAME}`
   - 校验必填字段
   - 输出标准配置对象

3. 实现配置版本管理
   - 生成配置版本 hash
   - 支持单 alias 版本识别

4. 实现热更新事件中心
   - `model-config-reloaded`
   - 文本域失效事件
   - 图像域失效事件

5. 工厂接入缓存失效
   - 定向失效单模型
   - 整域失效
   - 实例 `dispose()`

### 交付物

- `config/models.yaml` 模板
- `apps/web/src/server/loaders/model-loader.ts`
- 配置热更新事件模块

### 验收

- 修改 YAML 后无需重启即可触发配置重载
- 文本配置变化不影响图像工厂缓存
- 图像配置变化不影响文本工厂缓存
- 环境变量缺失可得到明确报错

---

## Phase 4：统一异常、日志、限流、重试

### 目标

让所有后续策略实现都基于统一异常与可观测能力开发，避免后补基础设施。

### 任务

1. 定义统一异常
   - `AIPictureBookStudioModelException`
   - 标准错误码
   - 厂商错误映射方法

2. 定义 JSON logger
   - 请求开始
   - 请求成功
   - 请求失败
   - 重试
   - 健康检查
   - 配置热更新

3. 实现基础能力组件
   - 超时控制器
   - 指数退避重试器
   - 模型级并发限流器

4. BFF 统一接入异常处理
   - 所有 API route 使用统一包装
   - 统一返回标准错误响应

### 交付物

- 异常模块
- 日志模块
- retry / timeout / rate limiter 工具
- BFF 统一响应包装器

### 验收

- 任意策略抛出的底层错误都能被映射为统一异常
- 所有生成调用都能打印带 `traceId` 的 JSON 日志
- 文本与图像模型并发限流互不影响

   - `/api/text-models/stream`

   - 提供文本模型下拉
   - 发起同步/流式调用

5. 替换现有文本模拟逻辑
   - 故事生成
   - 提示词优化
   - 其他文本相关场景

### 交付物

- 四个文本策略

### 验收

- 用户可在前台切换不同文本模型

## Phase 9：性能验收与上线准备

### 目标

围绕用户给定的验收指标做压测与上线前检查。

### 任务

1. 页面性能验证
   - `1000` 条模型配置渲染测试
   - 拖拽与编辑交互不卡顿

2. 接口性能验证
   - 测试连接响应验证
   - 并发文本/图像生成压测

3. 资源指标验证
   - `50` 路文本 + `50` 路图像并发
   - 监控内存增长与 CPU 使用率

4. 故障隔离演练
   - 单模型 Key 失效
   - 单厂商 Endpoint 不可达
   - 单域缓存重建

### 验收

- 页面渲染时间 < `300 ms`
- 测试连接响应 < `2 s`
- `50 + 50` 并发时：
  - 内存增长 < `200 MB`
  - CPU 占用 < `60%`
- 单模型失效时其他模型与业务零中断

## 交付顺序建议

推荐按以下顺序推进：

1. `Phase 0-1`
   - 完成 Next.js 迁移骨架
2. `Phase 2-4`
   - 建好双域平台基础设施
3. `Phase 5`
   - 文本模型先上线
4. `Phase 6`
   - 图像模型接入
5. `Phase 7`
   - 配置页面与热更新上线
6. `Phase 8-9`
   - 完成测试、CI、压测和上线准备

这样安排的原因是：

- 文本模型接入通常更快，更适合作为第一条真实链路
- 图像模型差异更大，放在第二条链路更稳妥
- 配置页面依赖底层能力稳定后再接，返工最少

## 风险控制

### 风险 1：Next.js 迁移过程中现有功能回退

控制方式：

- 保留原工程作为迁移对照
- 逐页迁移而非一次性重写

### 风险 2：厂商接口差异过大导致抽象失真

控制方式：

- 在策略层保留适配自由度
- 只统一真正通用的最小接口

### 风险 3：YAML 热更新与并发请求冲突

控制方式：

- 使用版本化配置
- 旧请求保留旧实例执行，新请求读取新实例

### 风险 4：图像模型响应慢影响整体体验

控制方式：

- 图像域单独限流
- 优先支持流式进度或轮询进度反馈

---

## 最终结果

完成本计划后，项目应具备以下能力：

- 已迁移到 `Next.js`
- 文本模型与图像模型双域彻底解耦
- 支持多厂商、多模型、多别名配置
- 支持同步生成、流式生成、健康检查、配置热更新
- 支持统一异常、统一日志、统一测试与 CI
- 支持后续以最小改动新增全新模型策略

该计划适合作为后续编码实施的唯一执行路线，推荐严格按阶段推进，不跨阶段混写。
